# Guest weapons and saved state

Protocol 11 routes client fire/reload controls to the host's guest inventory. A guest weapon uses its actor's position and aiming direction, and world weapon presentation instead of the host's primary HUD. Inventory slot and safemode callbacks avoid modifying the host's HUD through guest actions. Native weapon draw completion is required before the automated firing stimulus.

The host publishes guest health, power and radiation in normal sessions. It caches those values per character and captures native inventory records, including native item save data, placement, ammunition and active slot. It captures immediately before group travel, on disconnect when the native actor remains available, and on normal session shutdown; periodic capture preserves changes during a running session. Replacement destination actors restore the cached state. Restore waits for native inventory attachment before activating the saved slot. Native item packets remain host-local and are never accepted from peers.

Host-local files named `coopnet-character-<scope>-<character>-0` and `-1` retain alternating versions. The scope derives from the original loaded save name, native ALife version, supplied game/mod fingerprints and host character identity. Files are bounded and SHA-256 checked. Loading selects the newest valid matching record; an interrupted or damaged newest write leaves the other version available. These files do not overwrite native `.scop` saves. The selected save name is the campaign namespace; this does not implement globally portable characters or distinguish different campaigns reusing the same save alias.

The stored condition is limited to health, power and radiation. Full wounds/bleeding, money, faction/quest data and every mod-specific nested item relationship are not covered. Client inventory mirroring and normal loot/equipment UI requests remain incomplete, so the guest's local HUD inventory must not be treated as authoritative. The weapon integration test uses an explicit host-created pistol fixture; new ordinary guests do not yet receive a complete loadout.

Initial join timeouts retry automatically with a bounded backoff. An existing client process uses its resume token after connection loss. Client process restart into the same running host still needs a persisted resume credential; a new host process can load the character's saved equipment through a fresh join.

`test-coopnet-persistence.ps1` runs firing and group travel in isolated appdata, damages the newest disposable guest record, and starts new host/client processes to check recovery of the weapon, active slot and two remaining rounds. Original native saves are hash-checked throughout. See PROGRESS.md for completed native runs and logs.
