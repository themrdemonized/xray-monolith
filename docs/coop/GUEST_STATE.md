# Guest weapons and saved state

Protocol 22 runs guest fire/reload through the local native weapon for immediate animation, sound and predicted ammunition changes, while the same input goes to the host's native guest weapon. Guest bullets and explosion fragments/blast damage cannot send authoritative hits. The host owns hits, item transactions and final ammunition. Inventory views correct native ammunition when a new revision arrives instead of resetting it every render frame; exhausted local presentation items can be recreated if the host still owns them.

The Join dialog offers the native save picker and character creator. A loaded character sends a bounded typed inventory manifest before client readiness; peers never supply native spawn packets. The host validates item classes and upgrade membership, creates native session items, restores equipped/belt/backpack placement and the active slot, and sets the selected character's rubles. Owner-only inventory views now include rubles, addon flags/scope selection, upgrades and remaining consumable uses. Import is limited to 256 inventory items and 16 upgrades per item. Original single-player saves are not overwritten. A remembered host campaign character resumes its host journal; this is not a portable save of co-op progress across unrelated hosts. Mod-specific nested item state, secondary grenade magazines and character quest/faction/script data still need separate adapters.

Protocol 15 routes client fire/reload controls to the host's guest inventory. A guest weapon uses its actor's position and aiming direction, and world weapon presentation instead of the host's primary HUD. Inventory slot and safemode callbacks avoid modifying the host's HUD through guest actions. Native weapon draw completion is required before the automated firing stimulus.

The host sends bounded, owner-only inventory views containing section, condition, placement, active item and ammunition. The guest retires the copied host actor's inventory and creates local presentation items from that view. Inventory menu and quick-use requests route equip, backpack, belt, use, activate, holster and drop actions to the host, using the existing correlated request/replay checks. A fresh character receives a PM pistol, ammunition, a bandage and a PDA; an existing saved character restores its equipment, including an intentionally empty inventory, without granting the starter items again.

The host publishes guest health, power and radiation in normal sessions. It caches those values per character and captures native inventory records, including native item save data, placement, ammunition and active slot. It captures immediately before group travel, on disconnect when the native actor remains available, and on normal session shutdown; periodic capture preserves changes during a running session. Replacement destination actors restore the cached state. Restore waits for native inventory attachment before activating the saved slot. Native item packets remain host-local and are never accepted from peers.

Host-local files named `coopnet-character-<scope>-<character>-0` and `-1` retain alternating versions. The scope derives from the original loaded save name, native ALife version, supplied game/mod fingerprints and host character identity. Files are bounded and SHA-256 checked. Loading selects the newest valid matching record; an interrupted or damaged newest write leaves the other version available. These files do not overwrite native `.scop` saves. The selected save name is the campaign namespace; this does not implement globally portable characters or distinguish different campaigns reusing the same save alias.

Loose world inventory items now have bounded typed position, condition and ammunition updates. Guest pickup uses the host transaction path with native ownership, capacity and distance checks. Taking a persistent item withdraws it from the world registry without replacing its native data; dropping it restores persistent world ownership. Quest/story items and items containing children are excluded from ordinary loot transfers. Ordinary corpse and unlocked stash transfers use the host transaction path; quest dialogue/rewards remain unfinished. Temporary guest actors and presentation items explicitly bypass ALife registration at server creation.

The stored condition is limited to health, power and radiation. GCS2 also captures the host-owned native guest money balance and restores it across travel and host restart. Older GCS1 records preserve inventory without overwriting starting money. Money is now included in the guest presentation view; shared reward grants are unfinished. Full wounds/bleeding, faction/quest data and every mod-specific nested item relationship are not covered. Native control probes exercise the request queue used by inventory UI hooks; they do not verify clicked inventory menus or visual HUD appearance. Belt, use and holster still need dedicated native checks. The weapon integration test uses an explicit host-created pistol fixture. Identical inventory views are suppressed, and world positions are quantized to one centimetre to reduce idle traffic.

Initial join timeouts retry automatically with a bounded backoff. An existing client process uses its resume token after connection loss. Saved Windows-encrypted connection profiles let a new guest process resume against the same host. Expired host sessions retry fresh admission with the saved character identity; a new host process can load that character equipment.

`test-coopnet-persistence.ps1` runs firing and group travel in isolated appdata, damages the newest disposable guest record, and starts new host/client processes to check recovery of the weapon, active slot and two remaining rounds. Original native saves are hash-checked throughout. See PROGRESS.md for completed native runs and logs.

Protocol 15 adds host-validated respawn at a living teammate. Downed players keep equipment, and an all-dead party cannot respawn. Guest local death waits for host confirmation. See [Respawn](RESPAWN.md) for popup behavior and limits.

Protocol 16 mirrors the host's native quest journal and known story-info registry, and synchronizes NPC spawning/death/removal. Guest-owned faction data, mod-specific task tables, dialogue acceptance/turn-in and reward distribution remain separate unfinished work. See [Shared world](SHARED_WORLD.md).
