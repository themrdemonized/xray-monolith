# R1 XREAL Native: устройство, сборка и продолжение

## 1. Граница результата

Это воспроизводимый прототип перехвата рендера, а не законченная VR-интеграция. Его задача — подтвердить возможность отдельных геометрических видов без изменения EXE на диске и сохранить исходники для дальнейшей работы. Отсутствующие функции перечислены явно. Не считайте `PASS` теста доказательством комфортной игры в очках.

Исходная камера является **правым глазом**, а левый находится на `IPD` левее. Мышь и баллистика остаются в исходном игровом пути. Такой выбор позволяет сначала проверить обычный прицел, не меняя направление выстрела. Центр головы в этой модели не совпадает с исходной камерой; полноценный head tracking должен учесть это отдельно.

## 2. Точная база

Это кандидат исходной базы; побайтовое соответствие установленной EXE пересборкой не доказано. ABI исследован по соответствующим PDB.

## 3. Сборка без компьютера автора

Нужны Windows x64, VS 2022 C++ Build Tools с Windows SDK (D3D11, DirectXMath, BCrypt, PPL). MinHook уже лежит в `vendor/minhook`, его LICENSE.txt необходимо сохранить. Откройте x64 Native Tools Command Prompt for VS 2022, перейдите в каталог проекта и выполните:

```bat
R1_test_math.cmd
R1_test_gpu.cmd
R1_build.cmd
```

`R1_env.cmd` проверяет, что открыт x64 Developer Prompt. Код использует `/MT`, C++17, x64; `sizeof(Concurrency::task_group)==232` — обязательное ABI-условие. Совпадение размера не доказывает полную совместимость PPL другого toolset. При переносе проверяйте и поведение ожидания задач.

Выходная DLL: `package/gamedata/plugins/R1_XREAL_Native/R1_XREAL_Native.dll`. EXE, PDB, ресурсы игры и сохранения в распространяемый архив включать не надо. Полная пересборка движка для DLL не нужна. Исторические `R1_prepare*.py` используют локальные пути и не являются обязательным этапом.

## 4. Контракт загрузчика

Настоящие экспортированные функции перечислены ниже. Это API нашей DLL, а не встроенное API Anomaly.

```c
typedef struct {
    unsigned size, installed, enabled, pairs, passes, frame, restored;
    int error;
} R1Status;
int r1st_install(const char* log_path);
int r1st_set(unsigned enabled, float eye_distance_m, float convergence_m);
int r1st_status(R1Status* out);
int r1st_capture(const char* ppm_path);
int r1st_shutdown(void);
```

LuaJIT FFI-загрузчик показан в `tests/R1_live.script`. `ffi.load` получает путь через `getFS():update_path('$game_data$', 'plugins\\R1_XREAL_Native\\R1_XREAL_Native.dll')`. Установку, управление и выключение выполняет один поток. Перед чтением статуса `size=ffi.sizeof('R1Status')`. Успех большинства вызовов равен 1. DLL загружается выключенной; для продолжения стерео нужен `r1st_set(1, 0.064, 2)` чаще раза в 1500 мс. `r1st_set(0,...)` выключает стерео. Пропавший heartbeat прекращает стереорендер, но поле `enabled` не является отдельным индикатором свежести heartbeat.

Допустимый IPD 0..0.085 м, convergence 0.5..10000 м; это программные границы, не рекомендация выставлять крайние значения. Сброс IPD в ноль полезен для проверки совпадения видов. Функция capture пишет PPM из следующего успешного SBS-кадра, только для поддержанного RGBA8 backbuffer. Вызов не гарантирует, что файл уже записан: проверяйте файл и лог.

Ошибки: `-10` неизвестный хост/изменённые байты перехвата; `-11..-14` установка MinHook/закрепление DLL; `-2/-3` неверный поток/состояние/параметры; `-20` HDR/MSAA/SecondViewport; `-21` D3D targets; `-22` сменился frame между глазами; `-23` компоновка; `-24` неподходящее соотношение backbuffer. Не все ошибки установки дублируются в `status.error`: проверять нужно именно возвращённое значение.

## 5. Один кадр пошагово

1. `identify()` вычисляет SHA256 EXE на диске, проверяет x64 PE, timestamp/SizeOfImage, 24 байта каждой из трёх функций в памяти. Неизвестный хост не патчится.
2. MinHook перехватывает `CRender::Render`, `CRenderDevice::End`, `CHOM::MT_RENDER`. Адреса — `module_base + RVA`, ASLR не отключается.
3. `onRender` проверяет живой уровень, меню, heartbeat, владельца потока и поддержанные режимы. При отказе вызывает обычный renderer.
4. Перед заменой камер временно сбрасывает `Device.isRendering`, ждёт `secondary_tasks`, восстанавливает флаг. Это требуется из-за параллельных MT-задач и цикла Lua GC. Ожидание нуждается в дальнейшем аудите синхронизации; один успешный запуск не доказывает отсутствие всех гонок.
5. Сохраняет блок камер, обратные матрицы и aspect. Запоминает `Device.dwFrame`. HOM временно выключен, перехват `MT_RENDER` не даёт использовать кэш одного frame между двумя глазами.
6. Выставляет левую камеру, вызывает original Render и копирует backbuffer в left. Выставляет правую камеру, вызывает original Render и копирует в right. Симуляцию, обработку ввода и выстрел скрипт в этом цикле не запускает повторно.
7. Восстанавливает камеры, render cache и HOM. Проверяет неизменность frame. Счётчик `restored` означает выполнение пути восстановления, а не независимое побайтовое сравнение всех полей.
8. Перед original End полноэкранный треугольник пакует left/right в две половины. Deferred D3D context и `ExecuteCommandList(..., TRUE)` сохраняют состояние непосредственного контекста для вызывающего кода.

Оба временных вида имеют размер всего backbuffer, затем сжимаются по горизонтали в половину. Это затратно. Не обещать двукратный FPS или производительность single-pass stereo. В перспективе нужны отдельные targets размером одного глаза.

## 6. Матрицы и правый глаз

В `eye()` исходная позиция `P`, вектор вправо `R`, смещение `s`: `Peye=P+R*s`. Для правого `s=0`, для левого `s=-IPD`. В row-vector соглашении view умножается на translation `(-s,0,0)`. Projection `_11` умножается на 2, `_31 += s*_11/convergence`. Это параллельные камеры с off-axis projection, без toe-in.

У X-Ray `fASPECT` означает **height/width**, поэтому для половины широкого SBS он умножается на 2. Меняются обычные, HUD и Cam view/project/full, обратные матрицы и cache. Previous приравниваются к текущим, что не заменяет полноценные раздельные temporal histories.

При SBS 3840x1080 каждый глаз получает 1920x1080. В нашем оконном запуске запрошено 2560x720, фактический backbuffer — **2544x681**, что видно в сохранённом изображении. Меню может иметь иной layout. Проверять нужно фактический размер, а не строку выбора режима.

В `R1_stereo_math.h` есть эталон make_pair/project для unit tests. Нативный `eye()` применяет матрицы отдельно и не вызывает make_pair. Следующая полезная проверка — снять реальный снимок матриц и сравнить проекцию контрольных точек с эталоном.

## 7. Карта ABI

Все смещения ниже относятся только к указанным хостам. Источник профилей — `native/R1_hosts.h`; переносить таблицу по одному похожему имени EXE нельзя.

| Объект/поле | Смещение в байтах |
|---|---:|
| Device position/direction/up/right | 64 / 76 / 88 / 100 |
| view / HUD view / Cam view | 112 / 176 / 240 |
| projection / HUD / Cam | 304 / 368 / 432 |
| full / HUD / Cam | 496 / 560 / 624 |
| Previous для соответствующих матриц | текущее +576 |
| FOV / aspect | 1500 / 1504 |
| m_pRender | 2064 |
| isRendering | 2264 |
| inverse view/project/HUD project/full | 2320 / 2384 / 2448 / 2512 |
| SecondViewport / secondary_tasks | 2576 / 2584 |

## 8. Как переносить на новую EXE

1. Сохранить старый рабочий профиль; создать отдельную копию игры, appdata и save.
2. Получить **согласованную пару EXE/PDB** нужного релиза. Проверить CodeView RSDS GUID/age EXE против PDB через DIA/DbgHelp; если символы unmatched, остановить перенос.
3. Через символы установить адреса `CRender::Render`, `CRenderDevice::End`, `CHOM::MT_RENDER`, cache transforms/cache previous и проверки меню. Вычесть image base для RVA. Проверить дизассемблирование, calling convention, перегрузки, границы функций.
4. По PDB проверить каждый layout из таблицы, типы/размеры полей, PPL и все globals. Исходники читать параллельно: одинаковое имя функции не означает одинаковые побочные эффекты.
5. Сохранить SHA256, PE timestamp/SizeOfImage, GUID/age, 24 исходных байта каждой точки в отдельной записи профиля. Не удалять защиту и не заменять хеш только ради запуска.
6. Сначала проверить отказ на неподдержанном EXE и выключенный режим на поддержанном. Затем IPD=0, потом рабочий IPD. Отдельно проверить DX11 и AVX, а также конфликт с уже установленным hook.
7. Приложить исходники профиля, команды, свежие логи, кадры и хеш DLL. Назвать непроверенные пункты. Ни PDB lookup, ни компиляция не заменяют живой тест.

`R1_prepare.py` фиксирует происхождение исходного профиля, но опирается на toolkit предыдущего локального проекта. Для независимого порта разработчику нужен собственный DIA/DbgHelp dump либо переносимый extractor; такого extractor в этом прототипе нет. Текущий header уже содержит всё для сборки под две перечисленные EXE.

## 9. Воспроизведение игрового теста

Подготовить отдельный корень игры с собственным fsgame/appdata, ресурсами Anomaly и нужной EXE. Копировать сохранение с актёром и обычным пистолетом; не использовать оригинал рабочего save. Выключить TAA (`ssfx_taa (0,0,0,0)`), MSAA и HDR; не включать SecondViewport и ReShade depth stereo одновременно. Выбрать широкий SBS backbuffer. Не использовать `-nosound` для этого fixture: первый такой запуск давал поток ошибок отсутствующих звуков.

Положить DLL по указанному пути и два тестовых `.script` из `tests` в отдельный `gamedata/scripts`. Bootstrap DXML нужен для автоматического снятия меню/паузы исключительно в стенде. `R1_live.script` регистрирует `actor_on_update`, загружает DLL, активирует оружие из слота, включает стерео, снимает кадры, нажимает zoom/fire, выключает и завершает процесс. Он предполагает соответствующий save и использует обычные игровые API; это не автономный тест без игровых данных.

Сохранить `R1_live.log`, `R1_native.log`, свежий `xray_*.log`, `R1_stereo.ppm`, `R1_ads.ppm`. Проверить завершение без FATAL ERROR, изменение counters, размер кадра, порядок глаз, отсутствие вертикального рассогласования. Сравнить ближнюю/среднюю/дальнюю геометрию и поверхности, скрытые в одном глазу. PNG из evidence получен только преобразованием формата PPM, без дорисовки.

Матрица следующей приёмки: IPD=0; обычный IPD; неподдержанный хост; чужой hook; 16:9 отказ; таймаут heartbeat; enable/disable; меню; inventory/PDA; смерть; загрузка; смена уровня; DX11AVX; три расстояния до мишени; разные HUD FOV; обычный прицел/коллиматор/3DSS/SecondViewport; 30 минут игры. Для попаданий фиксировать исходный луч, центр правого глаза и место попадания, а не только расход патрона.

## 10. Что исправлять следующим

1. **UI:** в текущем End SBS перекрывает поздний 2D HUD. Нужен отдельный UI target/компоновка в оба глаза с правильным aspect и курсором; меню должно иметь предсказуемый режим. Не вызывать целиком игровую симуляцию второй раз ради UI.
2. **Состояние:** раскидать HOM/in_pair/isRendering по RAII, обработать частичную инициализацию GPU. Сейчас успешный `vs`/`left` может пережить отказ создания другого ресурса и ошибочно считаться готовым при повторном setup. Это известный дефект пути ошибки, не заявленная исправленная функция.
3. **Temporal/culling:** запретить неподдержанный TAA в runtime; разделить histories. `Calculate` и часть выбора света/сектора происходят до перехвата; одного HOM-off недостаточно для доказательства корректности на границах порталов. Аудировать оба глаза по реальным draw calls.
4. **Прицел:** проверить попадания и HUD transforms, отдельно обработать оптику/SecondViewport и дальние лучи. Не сдвигать баллистику, чтобы скрыть ошибку projection.
5. **Управление:** default-off MCM с названием `R1 XREAL Native`, явное отключение при неподдержанном режиме, сохранения/переходы, безопасная клавиша выхода. Phoenix UDP и независимый поворот головы ещё не встроены.
6. **Производительность:** перейти на eye-sized targets после корректности, измерить CPU/GPU время, а не выдавать counters за FPS.

## 11. Встраивание непосредственно в движок

Отдельная DLL доказывает подход без замены EXE, но устойчивый engine вариант должен владеть состоянием каждого глаза явно. В исходниках начинать с `src/xrEngine/device.cpp`, `src/Layers/xrRenderPC_R4/r4_R_render.cpp`, `src/Layers/xrRender/CHudInitializer.cpp`, `src/xrGame/HUDManager.cpp`, `src/xrGame/Actor_Weapon.cpp`.

Разделить simulation update и render-view. После завершения необходимых MT jobs сформировать две структуры вида с world/HUD matrices, targets, culling и histories; выполнить render-view для каждой; UI скомпоновать отдельно; Present один раз. Исходный aim ray сохранять до изменений камеры. Оптику оформить отдельным view, не переиспользовать глобальный SecondViewport без анализа. Это план интеграции, готового engine patch пока нет.

Для полной сборки движка следовать README исходного репозитория: получить submodules, открыть `engine-vs2022.sln`, установить нужные C++/MFC/ATL компоненты. Собирать тестовую EXE отдельно. Не подменять рабочую EXE результатом непроверенной сборки.

## 12. Передача и публикация

В review передавать исходники DLL, проверенные профили, MinHook с лицензией, сборочные команды, tests, RU/EN документацию и небольшие собственные evidence. Не передавать game db, сохранения, весь appdata или секреты. Снять patch из коммита: `git format-patch -1 HEAD --stdout > R1_XREAL_review.patch`; применить в отдельной ветке `git am R1_XREAL_review.patch`. Не выдавать addon patch за готовую интеграцию renderer в движок.

Draft PR должен прямо сказать: эксперимент, 2D HUD/оптика/temporal не готовы; просим review порядка render/MT jobs и предлагаем путь к явному per-eye render. При продолжении обновлять таблицу проверок, хеш DLL и логи. Название задачи и наличие форка не являются доказательством принятия upstream.
